# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A bot that plays chess on Lichess with human-like behaviour: neural-network move selection blended with Stockfish analysis, screen-capture board vision (OpenCV + template matching), and mouse automation. Entry point is `main.py`, which delegates to `clients/mp_original.py`.

## Environment

- Use `venv/bin/python` (3.12) — no bare `python` on PATH, and system `python3` lacks the dependencies.
- Lint only the files you touch: `venv/bin/ruff check <files>` (config in `ruff.toml`; ~170 pre-existing violations elsewhere, mostly unused imports).

## Verifying changes

The bot can't run end-to-end here — needs an X11 display and a live Lichess page. Never assume a live run is possible; use these offline checks and leave live verification to the user.

- **Engine parity harness** — `venv/bin/python -m unittest discover -s testing/engine_parity`. Real Stockfish + real NN weights (no mocks) against four fixed scenarios; the golden-master gate for the `engine.py`/`engine_components/` split. Run after touching either. Discrete outputs (move, mood, `decide_*`/`check_obvious_move`) are asserted exactly; eval-derived floats get jitter tolerance; `ponder`/`premove` aren't exact-matched (own wall-clock-capped scans make them non-reproducible). Re-record (`--record`) only when the behaviour change is intentional.
  - ⚠️ **Unreliable under load**: alongside a competing sweep it false-fails about half the time. Tell: runtime — normal is ~16s, 25-36s means something else is running (check `pgrep -f multiprocessing` for orphaned workers).
  - ⚠️ **A clean pass isn't proof a change is inert**: the four scenarios don't exercise every code path (e.g. a `REEVAL_ORDER` default flip passed unchanged despite being a real behaviour change — caught only by a dedicated unit test). Check the scenarios actually exercise your change before trusting green.
- **Engine-component unit tests** — `venv/bin/python -m unittest discover -s testing/engine_components`. Fast, pure-function, no Stockfish/display.
- **Client unit tests** — `venv/bin/python -m unittest discover -s testing/client`. Must stay green; every test is a regression from a real logged game. 7 of 34 import `chessimage` (needs X11) and error out as `_FailedTest` without a display — an environment limitation, not a regression. To exercise scan code on real frames, monkeypatch `capture_all_regions` to return crops saved under `logs/sessions/*/errors/` (production's real inputs; pruned to a 7-day window, so pull frames into a test before they age out).
- **Vision/calibration changes** — `venv/bin/python -m auto_calibration.calibration_readback_test --screenshots auto_calibration/offline_screenshots/desktop --profile desktop` (FEN/clock/turn/result detection + timing, production-identical functions).
- **Calibration fitting** — `venv/bin/python -m auto_calibration.offline_fitter --dir <dir> --profile <name> --site <lichess|chess_com> --extract-all --visualise`. Pass `--site` for non-Lichess — it picks the coordinate layout for player/rating rows. Output JSONs are gitignored, so a coordinate fix belongs in `coordinate_calculator.py`, not just the fitted JSON.
- `main.py --debug` (dry-run) / `--offline` (screenshot replay) when a display is available.

(The old mocked-Stockfish suite `testing/engine/` was deleted 2026-07-25 — it had been red for months after a refactor broke every test's patch target; the parity harness replaces it as the engine gate.)

## Key tuning knobs

`common/constants.py`: `DIFFICULTY`, `QUICKNESS` (move-time pacing), `MOUSE_QUICKNESS`, `RESOLUTION_SCALE` (1.0/2.0 for 1080p/4K). `main.py` flags override some per run.

**Strength dial** — `Engine(target_rating=N)` / `--target-rating N`, resolved via `common/strength_profiles.py`. **A pace dial, not a strength dial**: only `quickness` has a fitted rating mapping (mean emt), so move agreement and error rates are untouched by it. Snaps to `STRENGTH_LEVELS` (2200/2450/2700/2850; measured resolution is ~200-300 Elo) and returns `effective_rating`. Precedence: explicit knob argument > `target_rating` > module constant. One owning knob per measured feature (derivation: `docs/superpowers/specs/2026-07-27-strength-dial-design.md`):
- instant-move rate → `opening_book_fast_path` + ponder knobs
- top-1 match → `midgame_breadth_strength_bonus`, `reeval_order` (small effect, ~+0.02 each)
- blunder rate → no owning knob; not measurable at 150 games/arm (see cheat_detection below)

⚠️ `eval_noise_scale` is a **dead lever** for 1+0 (measured non-monotone, total span too small vs. the band table). ⚠️ `DIFFICULTY` is **frozen at 3** for 1+0 — it's an integer that couples base breadth and the noise floor, so it can't be aimed at one feature; may become tunable at longer controls where compute cost matters less.

**Client scan reliability** (`clients/mp_original.py`): `AWAITING_FRESH_SCAN` blocks further moves until a scan is adopted. Scans that fail move-linking/turn detection need a confirmation re-capture before adoption, skipped under `RESYNC_CONFIRM_MIN_TIME` seconds (deliberate — humans misread boards under time pressure too). The turn-unreadable fallback links via `common/utils.py:patch_fens`, which searches **full board width** rather than restricting to squares whose occupancy changed — the latter misses refill sequences, which is exactly what our own premove pairs do (e.g. `f1g2` then `e1g1` restores f1). Full-width search is only affordable via a placement-diff prune plus in-place board mutation (6.4s → 13ms on the worst real position); ply depth is capped at 3.

## Move-time pacing (`engine.py:_get_time_taken`)

How long the bot "thinks" is decided in `_get_time_taken`. Mechanisms, roughly in the order they apply:

- **Sharpness-driven complexity** (`_compute_sharpness`): win-probability spread across top candidates (multipv 5, depth 12), same definition as `cheat_detection`. Sharpness ≥ 0.25 is "critical" and slows the move down via a `((x+12)/25)**0.4` envelope. Replaced the old Lucas `activity`/`eff_mob` trigger (those metrics still feed mood/resign logic).
- **Intuition gate**: in a sharp position, only *sometimes* applies the slow-down and otherwise snaps quickly (`base_time *= 0.5`) — humans trust intuition on most critical moves rather than deep-thinking every one. Very flat positions (sharpness < 0.10) get a `*0.7` cut.
- **Per-game character** (`_sample_game_character`, resampled on ply-count-goes-backwards / `new_game()`): latent per-game draws (`game_pace_sf`, `game_premove_sf`, `game_ponder_snap_sf`, `game_scramble_fire_sf`, `game_snap_gate`, `game_scramble_skill`, `game_ponder_width`) that add between-game variance a per-move draw can't. Several share one latent normal with matching signs, because independent draws would half-cancel in the realised per-game instant rate. Constants `GAME_*`/`SCRAMBLE_*`. Related: `HUMAN_EVAL_NOISE_SCALE` trims eval-noise sd at both move-selection sites to raise engine-match rates without a compute cost — calibrate against innocent *single accounts*, not a variance ratio of 1.0 (pooled baselines are already under-dispersed vs. any real account; see cheat_detection below).
- **Flag-race autopilot** (`get_stockfish_move`, `FLAG_RACE_*`): below 10s of clock, evals in the scramble move-appeal formula are capped and occasionally dropped entirely (per-game via `game_scramble_skill`) — a flagging human doesn't distinguish "+mate" from "+800", both read as "winning", and picks by hand-distance and instinct. Without this the bot's endgame-ACPL tail is unhumanly thin. The same skill also gates scramble safety vetoes (`scramble_fire_veto`, `check_safe_premove`). ⚠️ **Twice-proven poison**: raising premove *queue* volume (mean bias > ~1.25, or a midgame full-premove channel) re-breaks blunder/match rates even when individually vetted — queued premoves fire after opponent deviations and after the clock has dropped, beyond any queue-time check. Tuning history: `cheat_detection/runs/variance_tuning_v1-v5.md`, `cheat_detection/runs/ralph/LOG.md` (gitignored).
- **Hesitation before the mistake, and the decisive snap** (`_adjust_time_for_move_loss`): after the move is chosen, its win-probability loss (from the deep sharpness scan) stretches think time when large (`MISTAKE_HESITATION_*`) or trims it when the move is clean (`MISTAKE_SNAP_*`) — restores the human-positive correlation between move time and move loss. Both skipped under 10s of clock. Constants and exact thresholds in `common/constants.py`.
- **Acting startled at an opponent blunder** (`mood_manager.check_opp_blunder`, flag read by `decision_logic.py` to multiply `base_time`): pauses before scooping up a piece the opponent just hung, rather than capturing with no reaction in the ~0.2s a clean best move otherwise gets from the decisive-snap branch. `_check_opp_blunder()` runs right after `check_obvious_move` and *before* `_get_time_taken` in `make_move` — it used to run at the very end (after the move's time was already decided) and got clobbered by `check_obvious_move`'s own reset of the same shared flag, so the mechanism was effectively dead until fixed 2026-07-28. Detection: a loose eval-swing pre-filter, then a scan of *every* opponent piece on the board (not just the one that moved, so leaving a piece en pris counts too) for the worst material recoverable in an exchange (`calculate_threatened_levels`), then an unexpectedness check — skip if it was the opponent's only legal move or a quick engine scan of the prior position already picked that exact move. Still fires under time pressure but muted, not skipped outright (unlike `MISTAKE_HESITATION`/`SNAP`): below `OPP_BLUNDER_STARTLE_LOW_TIME_THRESHOLD` (10s) own clock, the multiplier drops from 2.0 to 1.5. `OPP_BLUNDER_*` in `common/constants.py`.
- **Opening-book fast path** (`OPENING_BOOK_FAST_PATH`, ships **off**; `--opening-book-fast-path`): consults the book before analytics, so a memorised move skips the full scan and returns priced as an obvious move. The **only** lever that raises the opening instant-move rate (opening think time already sits below the per-move compute floor, so no pacing knob touches it). Skips `check_obvious_move` (acceptable — a real blunder takes the game out of book) and queues a book-derived premove (otherwise starves that channel). ⚠️ Off by default: added premove volume isn't cleared against `blunder_rate_timepressure`, which isn't measurable at 150 games/arm.

**Judge timing tails per rating band, never against the pooled 2300+ mean** — the pooled figure averages a population no individual sits at (e.g. it made the bot's already-well-calibrated mean emt look like a shortfall). Instant rate (emt < 1s) *rises* with rating; long-think rate *falls* — independent axes, and the bot is low on both, which is distributional narrowness no pace knob fixes since `quickness` scales the whole distribution rather than reshaping it. Per-phase: midgame long-think is already at the human rate; opening/endgame are structurally suppressed by their own compression formulas — raising the midgame multiplier would overshoot the one phase already right. Tracked tables: `cheat_detection/runs/elo_progression/report_timing.md`, `report_longthink.md`.

## Opening repertoire (`engine_components/opening_book.py`)

Sampling `bullet.bin` proportional to its own weights fresh each move spreads entropy far wider than real bullet players, who fall back on a handful of memorised systems. `consult_book(engine, board)` layers a small, hand-curated `engine.repertoire_book` (top `OPENING_REPERTOIRE_TOP_N`) in front of the broad `engine.opening_book` (`bullet.bin`, top `OPENING_BOOK_TOP_N`) — uncovered positions fall through to the broad book, then NN move probabilities. Both `Engine.get_human_move` and `premover.py:get_premove` call the same function, so live moves and premoves can't drift onto different books.

The repertoire is mined from a real Lichess account's move-frequency habits via the player opening-explorer API (needs an `Authorization: Bearer <token>`; the bulk PGN export endpoint is unusable in some sandboxes). Real per-account distributions are already appropriately peaked — measured frequencies are used directly as polyglot weights, no artificial sharpening. `scripts/utilities/build_repertoire.py` hand-packs `repertoire.bin` from a `LINES` list (python-chess's `chess.polyglot` only reads books, not writes); re-run after editing `LINES`. Coverage is deliberately narrow (~4-6 plies, only directly-measured branches) — an opponent deviating from mined lines falls through rather than being covered by invented theory.

## Architecture pointers

- `engine.py` — move selection core (`Engine`). Strangler-fig extraction: `engine.py` is the thin composition root (`__init__`, `make_move`, `close_engines`) plus one-line delegators; logic lives in `engine_components/` (`simple_decisions.py`, `state.py`, `mood_manager.py`, `stockfish_move_logic.py`, `human_move_logic.py`, `decision_logic.py`, `game_character.py`, `premover.py`, `ponderer.py`), each a plain-function module taking the `Engine` instance as an explicit first argument. Verified extraction-by-extraction against `testing/engine_parity/` (real-Stockfish golden-master, not mocked). Signature-narrowing (specific primitives instead of the whole `engine` instance) is deliberately out of scope. `testing/engine_parity/test_snapshot.py` documents two quirks this surfaced: `calculate_analytics`'s quick scan leaves load-dependent transposition-table state that perturbs later same-process scans; `ponder`/`stockfish_ponder`'s wall-clock-capped scans make exact candidate lines non-reproducible (only line *count* is stable).
- `models/alter_move_prob_nn.py` — `AlterMoveProbNN`, the trained net that reshapes NN candidate distribution; loaded in `Engine.__init__`, so it's production code even though `development/` holds its training scripts (which now train *into* the live weights path).
- `common/search_constants.py` — search-breadth/scan-width tuning constants, documented per-constant in the file.
- `engine_components/opening_book.py` — shared repertoire/general-book consultation, see above.
- `clients/mp_original.py` — the only client (mouse automation, game loop, scan-reliability guards). Older variants were deleted 2026-07-25 (`git log --diff-filter=D` recovers them).
- `sites/` — *how a site behaves* (game start/end, resign/lobby flows), vs. `auto_calibration/`'s *where things are*; a profile binds both via `calibration_info.site`. chess.com's clock never moves between game states, so it needs different signals than Lichess: game end is the dark result modal (not a "clock readable" check); game start needs positive evidence (the move-nav bar) because the lobby's preview board looks identical to a fresh game. Same reasoning behind `Site.live_game_on_screen()`: chess.com asks whether the clock is *ticking* rather than merely readable. Details: `docs/site-abstraction.md`.
- `common/utils.py` — `scraped_fen_sanity_issues()`/`InvalidPositionError` reject structurally impossible scraped positions (Stockfish would segfault). Two layers: default checks placement only (the raw scrape always claims white to move, so turn-dependent tests would false-positive); `turn_reliable=True` (engine only) additionally flags a side-not-to-move-in-check position, which segfaults Stockfish deterministically. Don't merge the layers.
- `chessimage/image_scrape_utils.py` — screen capture, FEN extraction, clock/rating OCR. `rating_from_words()` prefers a bracketed number (chess.com's `username (1453)` layout) over a bare one, to avoid reading a username's own digits as a rating. Last-move highlight colours (`FALLBACK_COLOUR_SCHEME`) must never sit within tolerance of Lichess's selected-square tint, or a stale premove selection reads as a last-move highlight and poisons turn detection (`testing/client/test_highlight_colours.py`).
- `auto_calibration/` — fits board/UI coordinates from screenshots. Site-independent except the player/rating rows (Lichess: beside the clock; chess.com: above/below the board) — fitting one site's screenshots with the other's geometry silently misreads ratings.
- `common/move_timing.py` — timing formulas (mouse-leg duration, settle sleeps, ponder/scramble waits) shared between the live client and simulator. Tune here, not inline in the client, or the two drift apart.
- `simulation/` — offline self-play with simulated clocks (no display/mouse). `python -m simulation.run --games N --tc 60+0 --workers 5` writes PGNs that feed straight into `cheat_detection`. Personas differ per bot via `--a-*`/`--b-*`; `--sides alternate` swaps colours with correct PGN headers. Drives the same `Engine` as live play. Machine-specific latency calibration: `python -m simulation.calibrate {detection,compute}`.
- `cheat_detection/` — offline human-likeness diagnostic (`analyze.py` CLI, `gui.py` Tkinter with a Simulation tab). Analysis depth defaults to 10; bot analysis and the baseline JSON **must use the same depth**. Corpus policy: 2300+ only (`fetch_corpus --any-player --band 2300 + N`); main baseline `baselines/bullet_1plus0_2300_plus.json`. Flagging: effect-size `|z| >= 2` or Welch t-test, plus a Brown–Forsythe variance test (⚑v) for un-human game-to-game consistency.
  - ⚠️ Judge ⚑v flags against innocent *single accounts*, not a variance ratio of 1.0 — pooled baselines are already under-dispersed vs. any real account (`runs/single_account_calibration.md`). Check flag persistence at innocent sample sizes first: `python -m cheat_detection.subsample_check <report.json>`.
  - ⚠️ **`blunder_rate` carries no information at 150 games/arm** — its real between-seed spread is ~3.6× the binomial standard error, so two identical-config arms can differ more from each other than from the baseline. Needs ~600 games/arm; `t1_rate` is sound at 150.
  - **Don't optimise against the pooled-baseline mean** — no real account is "average" (innocents with 600 games fail several Welch tests at p≈1e-10). Build a between-player dispersion file (`python -m cheat_detection.player_dispersion`) and judge with `python -m cheat_detection.outlier_check --dispersion <json>` instead; target mean|player_z| ≈ 0.8, not 0 (too-average is its own tell).
  - ⚠️ **Simulated PGNs contain no scramble moves** (truncated at `CLOCK_THRESHOLD_FRACTION * initial_time`) — compare against a truncation-matched corpus baseline or every bot error metric reads far too low. ⚠️ **`blunder_rate`/`mean_wc_loss` saturate in decided positions** — equalise score before comparing arms, lean on ACPL/match rates instead. Details: `docs/position-conditioned-human-likeness.md` (also notes the match-rate deficit is entirely in quiet positions, where error rates are already human — no strength lever fixes it).
