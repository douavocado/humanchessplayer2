# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A bot that plays chess on Lichess with human-like behaviour: neural-network move selection blended with Stockfish analysis, screen-capture board vision (OpenCV + template matching), and mouse automation. Entry point is `main.py`, which delegates to `clients/mp_original.py`.

## Python environment

Use the repo virtualenv: `venv/bin/python` (Python 3.12). There is no bare `python` on PATH, and the system `python3` lacks the dependencies.

## Lint

`venv/bin/ruff check <changed files>` (config in `ruff.toml`; stylistic rules that clash with existing code idioms are disabled). The repo has ~170 pre-existing violations (mostly unused imports/variables), so lint only the files you touched, not the whole tree.

## Verifying changes

The bot cannot be run end-to-end here — it needs an X11 display and a live Lichess page. Never assume a live run is possible; use the offline checks below and leave live verification to the user.

- **Engine tests**: `testing/engine/` (19 mocked-Stockfish tests) was deleted on 2026-07-25. It had been red for months — every test patched `engine.STOCKFISH`, a module-level attribute that became the per-instance `self.stockfish_engine` in a refactor — and a permanently-red suite trains you to skim past red output. The parity harness below covers the same `decide_*`/`check_obvious_move`/mood/move-choice surface against *real* Stockfish, which is better evidence than a mock. Use it as the engine gate; recover the old suite from git history if you ever want the plumbing tests (`test_init`, `test_write_log`, `test_update_info`, `test_set_target_time`) back.
- **Engine parity harness** (`testing/engine_parity/`): `venv/bin/python -m unittest discover -s testing/engine_parity` — real Stockfish + real NN weights (no mocks) against four fixed scenarios, the golden-master regression gate for the `engine.py`/`engine_components/` split. Run this after touching anything in `engine_components/` or the delegator methods in `engine.py`; a clean pass means the extraction changed nothing observable. Discrete outputs (move chosen, mood, every `decide_*`/`check_obvious_move` result) are asserted exactly; continuous eval-derived floats (`sharpness`, `lucas_win_prob`, `time_take`) get tolerance wide enough to clear real machine-load-driven Stockfish jitter (see module docstring); `ponder`/`stockfish_ponder` are summarized to a line count rather than exact-matched (their own wall-clock-capped scans make exact candidate lines non-reproducible); `premove` is recorded but not asserted (same jitter, occasionally flips a discrete decision). Re-record with `--record` only when a change is meant to alter behaviour — that redefines what "correct" means for every future run. ⚠️ **Do not trust this harness under load**: run alongside a 6-worker sweep, `lucas_win_prob` swings 30-40 points (vs the ~12 documented above) and it false-fails about half the time. The tell is *runtime* — a normal run is ~16s; 25-36s means something else is competing, including orphaned `multiprocessing` workers left by a killed sweep (check `pgrep -f multiprocessing`). Two false failures were nearly attributed to unrelated changes on 2026-07-28. ⚠️ **Green parity is not automatically proof a change is inert**: the four scenarios reach the `get_human_move` re-evaluation draw only degenerately (R=0, R=1, or R >= N), so the `REEVAL_ORDER` default flip passed unchanged despite being a real behaviour change worth +0.013 t1 — guarded instead by `testing/engine_components/test_reeval_order.py`. Check whether the scenarios actually exercise your code path before reading a pass as a proof.
- **Engine-component unit tests**: `venv/bin/python -m unittest discover -s testing/engine_components` — pure-function tests for logic extracted out of the engine, fast and dependency-free (no Stockfish, no display). Currently: `compute_ambiguity`, whose window must stay equal to `cheat_detection`'s `ambiguity_wc_window` or the snap-gate sweep is tuned against a quantity the analyser never measures (one test asserts exactly that); `test_book_fast_path.py` (the fast path arms only on a book hit and never leaks into the next move); `test_reeval_order.py` (the three orderings select genuinely different candidate sets — the parity harness does not cover this); and `test_strength_profiles.py` (the dial only ever sets knobs listed in `CALIBRATED_KNOBS`, and explicit arguments beat `target_rating`).
- **Client unit tests**: `venv/bin/python -m unittest discover -s testing/client` — these pass and must stay green. Note 7 of the 34 import `chessimage`, which imports `fastgrab._linux_x11`, so they error out as `_FailedTest` on a machine without X11 — that is an environment limitation, not a regression; check against a clean tree before believing you broke them. Every one is a regression from a real logged game, and each file's docstring says which: the unreadable-turn fallback and the highlight colour table (a flagged game), the scan-to-scan move linker, the chess.com game-page test and pre-seek guard, and rating OCR. ## Key tuning knobs

Behaviour is tuned via `common/constants.py`: `DIFFICULTY`, `QUICKNESS` (move-time pacing), `MOUSE_QUICKNESS` (cursor speed), `RESOLUTION_SCALE` (1.0 for 1080p, 2.0 for 4K). `main.py` flags override some of these per run.

**Strength control surface (2026-07-28).** One owning knob per measured feature; a second knob is never reached for to fix a feature that already has an owner. Full derivation and per-phase measurements in `docs/superpowers/specs/2026-07-27-strength-dial-design.md`.

| feature | owner | calibrated to a rating? |
|---|---|---|
| mean emt | `quickness` | ✅ `emt = 0.1964*q + 0.6234`, spans the whole band table |
| instant-move rate | `opening_book_fast_path`, ponder knobs | ❌ |
| top-1 match | `midgame_breadth_strength_bonus`, `reeval_order` | ❌ (~+0.02 each; the band table needs 0.05) |
| blunder rate | — | ❌ not measurable at 150 games/arm (see below) |

`Engine(target_rating=N)` / `--target-rating N` (both `main.py` and `simulation.run`) resolves a rating to knobs via `common/strength_profiles.py`. **It is a pace dial, not a strength dial** — only `quickness` has a fitted mapping, so move agreement and error rates are untouched. It snaps to `STRENGTH_LEVELS` (2200/2450/2700/2850) because the measured resolution is ~200-300 Elo, and returns `effective_rating` so callers can see the snap. Precedence, tested: **explicit knob argument > `target_rating` > module constant**.

⚠️ `eval_noise_scale` is a **dead lever** for t1: measured non-monotone across 0.25-0.95 (0.3556 / 0.3429 / 0.3514 / 0.3338 / 0.3331), total span 0.0225 against a band table needing 0.0504. Don't reach for it. ⚠️ `DIFFICULTY` is frozen at 3 for 1+0 — it is an integer, and it drives base breadth *and* the noise floor together so it can't be aimed at one feature. That freeze is 1+0-specific: at longer controls the compute-cost objection weakens and it may become the primary strength axis.

Client-side scan reliability lives in `clients/mp_original.py`: after making a move, `AWAITING_FRESH_SCAN` blocks further moves until a scan is adopted (prevents duplicate/out-of-turn clicks off stale vision), and board scans that fail move-linking or turn detection must survive a confirmation re-capture before being adopted — skipped when our clock is under `RESYNC_CONFIRM_MIN_TIME` seconds (deliberate: humans misread boards under time pressure). When the turn is unreadable, the fallback links the scraped placement from the last tracked fen under *both* turn hypotheses and adopts the fewest-plies candidate — `patch_fens` can "confirm" the wrong turn with a longer piece-shuffle line, which once handed the move to the opponent and flagged a won game (2026-07-12). The linker itself (`common/utils.py:patch_fens`) searches **full width** and deepens a ply at a time: restricting candidates to moves leaving a square whose *occupancy* changed misses every sequence that refills the square, which is exactly what our own premoves do (`f1g2` then `e1g1` puts a rook back on f1) — that cost ~1.3 full history wipes per game on chess.com (2026-07-25). Full width is only affordable because of the placement-diff prune (a ply closes ≤4 squares) plus in-place board mutation: 6.4s → 13ms on the worst real position, and shortest-first is what the turn fallback's ply ranking relies on. Ply counts are still capped at 3 (`depth_lim`); genuinely unlinkable scans (a piece dropped by a misread) must stay unlinkable.

## Move-time pacing (`engine.py:_get_time_taken`)

How long the bot "thinks" per move is decided in `Engine._get_time_taken`. A "complicated position" — one worth spending more time on — is keyed off **sharpness** (`self.sharpness`, computed in `_compute_sharpness`): the win-probability spread across the engine's top candidates from a narrow, slightly-deeper scan (multipv 5, depth 12), using the same logistic and definition as the `cheat_detection/` human-likeness analyser. Sharpness ≥ 0.25 is a "critical" position. This replaced the older structural trigger (Lucas `activity`/`eff_mob`); those Lucas metrics are still computed and used elsewhere (mood, resign logic), just no longer for time-scaling. Sharpness maps onto the same `((x+12)/25)**0.4` envelope, so the *magnitude* of the slow-down is unchanged — only the trigger.

An **intuition gate** stops the bot over-thinking (and flagging on time): in a sharp position it applies the slow-down only some of the time and otherwise snaps the move quickly (`base_time *= 0.5`), mirroring that humans trust intuition on most critical moves. Very flat positions (sharpness < 0.10) get a `*0.7` "little at stake" cut. All three log to `engine.log` (sharpness value, multiplier, gate outcome).

**Per-game character** (`_sample_game_character`, resampled whenever `update_info` sees the ply count go backwards — the engine instance persists across games; `new_game()` forces it): draws that vary *between* games what per-move noise can't. `game_pace_sf` (lognormal, scales every think time; applied **after** the phase/mood envelopes because the opening's `**0.2` compression crushes upstream factors; carries a `GAME_PACE_MEAN` 0.90 bias — the 2500-2800 band moves faster; note a mean-pace trim also compresses between-game movetime variance by the same factor). One latent snappiness normal drives `game_premove_sf` (scales every premove-search probability in `make_move`, incl. takeback-only and ponder-dic searches; plus a rating-based snap boost — vs weaker opponents confidence shows up in the premove channel, not think time, because the engine-compute floor means shorter think times can't create <1s moves), `game_ponder_snap_sf` (with pace, via `Engine.ponder_pace_sf`, scales the `ponder_response_wait` — ponder hits are ~30% of moves sitting at the 1s "instant move" boundary), and `game_scramble_fire_sf` (scales the <10s stale-ponder fire probability) — coupled with matching signs because independent draws half-cancel in the realised per-game instant rate. The premove/ponder draws carry deliberate mean biases (`GAME_PREMOVE_MEAN`/`GAME_PONDER_SNAP_MEAN`): mean-1.0 multipliers are *not* mean-preserving in realised rates (probabilities saturate at the top; the instant cutoff is a threshold). The same latent drives `game_ponder_width` (per-game cap on how many opponent replies `ponder()` prepares, clip 0–5; width 0 = a game that never pre-thinks) — the cap only binds because `PONDER_TIME_PER_POSITION` (`common/search_constants.py`, 0.05) stops the ponder budget pinning realised width at 1, which is why width draws did nothing at the old 0.1s/position. Separately: `game_snap_gate` (the intuition-gate probability, Uniform(0.55, 0.95) — raised after the time-vs-sharpness correlation overshot humans) and `game_scramble_skill` (flag-race composure, below). Constants `GAME_*`/`SCRAMBLE_*` in `common/constants.py`. Related strength knob: `HUMAN_EVAL_NOISE_SCALE` (0.75) trims the eval-noise sd at both selection sites — raises top-N engine-match rates toward the 2500-2800 band with no compute cost (unlike a DIFFICULTY bump); diminishing returns below ~0.75. Rationale: cheat_detection's Brown–Forsythe variance test flagged the bot as far too consistent game-to-game — but calibrate targets against innocent *single accounts*, not ratio 1.0 (see cheat_detection below).

**Flag-race autopilot** (`get_stockfish_move`, constants `FLAG_RACE_*`): below 10s of clock, evals in the scramble move-appeal formula are capped — a flagging human reads "+mate" and "+800" both as "winning" and picks by hand-distance and instinct, occasionally missing mates or throwing the win. Without this the bot's endgame-ACPL tail is unhumanly thin (humans: ~20% of games contain a 300+ acpl endgame, tail to 9000+ from thrown mates). The cap is per-game via `game_scramble_skill` u~U(0,1): cap = 550 + u·550, plus a blind-move chance 0.10·(1−u)² that drops evals entirely for one decision (pure hand-distance + noise — that's what actually throws a won ending). The same skill gates the scramble safety vetos with probability 0.75+0.25·u (`SCRAMBLE_VETO_P_*`): `scramble_fire_veto` (common/utils.py; both clients) suppresses blind stale-ponder fires that would drop a piece on a visibly-attacked square, and `get_premove` requires `check_safe_premove` for non-takeback scramble premoves. Both clients also check the **exact ponder hit first in scrambles** (under 10s, if the opponent played the prepared-for move, fire the prepared reply before considering stale fires) — quality instants: 2500-2800 humans fire ~60% of sub-10s moves instantly and those are their *safest* bucket (`python -m cheat_detection.emt_buckets`), while blind fires were the bot's worst. Tuning history (why these exact shapes: absolute vetos collapse the ACPL body/tail, a full 0–1 skill gate floods hang-fires back, and the *appeal-path cap never was the blunder source* — the excess sat in emt-0 instant fires): `cheat_detection/runs/variance_tuning_v1-v5.md`, and the 2500-2800 loop arc in `cheat_detection/runs/ralph/LOG.md` (both gitignored). ⚠️ Twice-proven poison: raising premove *queue* volume (mean bias > ~1.25, or a midgame full-premove channel — even `check_safe_premove`-vetted) re-breaks the TP blunder rate and match rates; queued premoves fire after opponent deviations and after the clock has dropped, beyond any queue-time vet. Widening `SCRAMBLE_FIRE_SF` trades instant-rate variance ~1:1 against TP blunders — the remaining instant-variance residual needs opponent-time pondering (architectural), not more fire volume. The two "close the game" overrides in the same function are deliberately soft (0.4 mate-dash, 0.15 low-piece), and `_decide_human_filters` routes more deep-scramble moves through this fallible path. Costs real win rate in flag races — that's the point.

**Hesitation before the mistake — and the decisive snap** (`_adjust_time_for_move_loss`): after the move is chosen, its win-probability loss is read from the stored deep sharpness scan (`self.sharpness_scan`, depth 12 multipv 5; the 20ms-capped full-width analysis is only a fallback — its evals are too noisy to gate on, which is why the original lever barely worked). Loss ≥ `MISTAKE_HESITATION_WC_LOSS` (0.05): think time stretched ×Uniform(1.4, 2.6) with probability 0.88. Loss ≤ `MISTAKE_SNAP_WC_LOSS` (0.02): trimmed ×Uniform(0.65, 0.9) with probability 0.7 — humans bang out moves they're sure of, and the trim keeps mean move time level despite the stretches. (0.75/0.6 → 0.88/0.7 for the 2500-2800 band's stronger correlation.) Both skipped under 10s of clock (plain clock veto; the old "hurry-mood" veto made the 15s constant unreachable). Restores the human-positive per-game correlation between move time and move loss (humans ≈ +0.11 in the diff150-300 population; measured 0.02 → 0.05–0.06 across validation sims — the engine's errors come from the human-probability sampling and are otherwise independent of think time). `MISTAKE_*` in `common/constants.py`.

**Acting startled at an opponent blunder** (`mood_manager.check_opp_blunder`, `engine.opponent_just_blundered` read by `decision_logic.py` to double `base_time`): gates the human reaction of pausing before scooping up a piece the opponent just hung, instead of capturing it with no reaction in the ~0.2s an obviously-best move otherwise gets from `_adjust_time_for_move_loss`'s decisive-snap branch above. `_check_opp_blunder()` runs in `make_move` right after `check_obvious_move` and *before* `_get_time_taken` — it used to run at the very end of `make_move`, after that move's time was already decided, so the flag it set could only ever affect the *next* move's pacing (and was then immediately clobbered by `check_obvious_move`'s own unconditional reset of the same flag for its unrelated "recapture wasn't really a takeback" case, before `decision_logic.py` ever read it — the mechanism was effectively dead). `check_obvious_move` still does the once-per-call reset; `check_opp_blunder` only ever ORs a `True` on top. Detection: an abs eval-swing pre-filter (`OPP_BLUNDER_EVAL_SWING_MIN`, 50 — loose on purpose, since a fixed cp threshold saturates in already-winning positions where hanging a whole rook barely moves the eval) gates a scan of *every* opponent piece still on the board (not just the one that moved) for the worst material recoverable in an exchange (`calculate_threatened_levels`, covers both putting a piece en pris and leaving one hanging elsewhere), thresholded at `OPP_BLUNDER_EN_PRIS_MIN_VALUE` (3 pawns). Then an unexpectedness check: skip if it was the opponent's only legal move, or if a quick depth-8 scan of the prior position would have picked that exact move anyway (i.e. it wasn't something we couldn't have predicted, just the least-bad option under a threat). `OPP_BLUNDER_*` in `common/constants.py`.

**The two timing tails move in opposite directions with rating, and are independent axes** (`cheat_detection/runs/elo_progression/report_longthink.md`, tracked). Instant rate (emt < 1s) *rises* with rating, 0.312 -> 0.369; long-think rate (emt > `long_think_secs`, 2s = initial_time/30) *falls*, 0.122 -> 0.088. The bot is low on **both**, which is distributional narrowness that no pace knob fixes — `quickness` scales the whole distribution rather than reshaping it.

Judge these per band, never against the pooled 2300+ mean: the pooled figure averages a population no individual sits at, and comparing against it made the bot's mean emt (1.04-1.06, i.e. ~2700) look like a shortfall needing correction when it is one of the better-calibrated things about it. Per-phase long-think rates: bot midgame 0.130 is already at the 2800+ human 0.125, but opening (0.002 vs 0.014) and endgame (0.007 vs 0.013) are structurally suppressed by their own time formulas — `base_time = (base_time ** 0.2)/2` compresses the opening toward ~0.57s, and the endgame takes `*0.7`. **Raising the midgame multiplier would overshoot the one phase that is already right.**

**Opening-book fast path** (`OPENING_BOOK_FAST_PATH`, ships **off**; `--opening-book-fast-path`): consults the book in `update_info` *before* `calculate_analytics`, so a memorised move stops paying for a full-width multipv scan plus an uncapped depth-12 sharpness scan, and `make_move` returns it priced as an obvious move. It is the **only** lever that raises the opening instant-move rate — the engine's requested opening think time already sits below the per-move compute floor (~0.85s of detection + engine + mouse), so no pacing knob touches it. Measured over 150 games: opening instant rate 0.373 -> 0.567 against a human 0.565, aggregate 0.260 -> 0.294. It skips `check_obvious_move`, which is acceptable because a real blunder takes the game *out* of book (0 of 822 measured book hits had a hanging queen or rook), and it queues a book-derived premove (`opening_book.book_premove`) because returning early otherwise starves the premove channel it competes with (14.0% -> 5.8% without it). ⚠️ Still **off by default**: the added premove volume is not cleared against `blunder_rate_timepressure`, which is not measurable at 150 games/arm.

## Opening repertoire (`engine_components/opening_book.py`)

The naive fix — sampling `bullet.bin` proportional to its own stored weights every move, fresh each call — spreads entropy far wider than real bullet players, who fall back on a handful of memorised systems rather than re-deriving an opening each game. `consult_book(engine, board)` layers a small, hand-curated `engine.repertoire_book` (consulted first, top `OPENING_REPERTOIRE_TOP_N`) in front of the broad `engine.opening_book` (`bullet.bin`, top `OPENING_BOOK_TOP_N`; both in `common/search_constants.py`) — a position not covered by the repertoire falls through to the broad book, then to NN human-move probabilities, unchanged. Both `Engine.get_human_move` and `engine_components/premover.py:get_premove` call the same function, so live moves and premoves can't drift onto different books.

The repertoire itself is not invented — it's mined from a real Lichess account's actual move-frequency habits via the player opening-explorer API (`https://explorer.lichess.org/player?player=<name>&color=<white/black>&speeds=bullet`, walked deeper with `&play=<uci,uci,...>`; needs an `Authorization: Bearer <token>` personal access token — unauthenticated requests 401, and the bulk `/api/games/user/` export endpoint is unusable in some sandboxes regardless of auth, hence the explorer instead of raw PGN mining). Real per-account distributions are *already* appropriately peaked (e.g. one account's actual data: 65.4% of White games open 1.Nf3, then ~80% follow with 2.g3 regardless of Black's reply) — no artificial sharpening needed, the measured frequencies are used directly as polyglot weights. `scripts/utilities/build_repertoire.py` hand-packs `repertoire.bin` from a `LINES` list (`(prefix_uci_moves, our_move_uci, weight)`) since python-chess's `chess.polyglot` module only *reads* books, not writes them; re-run it after editing `LINES`. Coverage is deliberately narrow (only directly-measured branches, ~4-6 plies deep) — depth and root breadth beyond that is a deliberate scope call, not a data limitation, so an opponent deviating from the mined lines is expected to fall through rather than being covered by invented theory.

## Architecture pointers

- `engine.py` — move selection core (`Engine`, imported by the live client and simulator both). Structured as a strangler-fig extraction: `engine.py` itself is now the thin composition root (`__init__`, `make_move` orchestrating everything, `close_engines`, ~832 lines) plus one-line delegator methods; the actual logic lives in `engine_components/` (`simple_decisions.py`, `state.py`, `mood_manager.py`, `stockfish_move_logic.py`, `human_move_logic.py`, `decision_logic.py`, `game_character.py`, `premover.py`, `ponderer.py`), each a plain-function module taking the `Engine` instance as an explicit first argument (`def decide_resign(engine): ...`, called via `Engine._decide_resign(self): return simple_decisions.decide_resign(self)`). This replaced an earlier abandoned attempt at the same split (a genuinely parallel, unwired tree that drifted and had a porting bug — ported the dormant hand-crafted move-prob heuristic instead of the live NN path); this time there is only ever one live implementation, verified extraction-by-extraction against `testing/engine_parity/` (real-Stockfish golden-master harness, not mocked) so nothing can silently diverge again. Signature-narrowing (passing specific primitives instead of the whole `engine` instance) was deliberately left out of scope — the mechanical move-and-delegate pattern is what made the extraction safe; tightening interfaces is optional future work once it's proven stable in production. See `testing/engine_parity/test_snapshot.py` for two engine.py properties this surfaced: (1) `calculate_analytics`'s 20ms-capped quick scan leaves load-dependent transposition-table state behind that measurably perturbs later same-process scans (`sharpness` drift ~0.06 on its [0,1] scale, `lucas_win_prob` occasionally ~12 points on its 0-100 scale) — pre-existing, not a harness bug; (2) `ponder`/`stockfish_ponder`'s own wall-clock-capped scans make which *specific* candidate lines they return non-reproducible run-to-run (line *count* is stable, exact dict keys aren't) — the harness summarizes rather than exact-matches those.
- `models/alter_move_prob_nn.py` — `AlterMoveProbNN`, the trained net that reshapes the NN candidate distribution. `Engine.__init__` loads it (weights `ALTER_MOVE_PROB_WEIGHTS_PTH`), so it is production code; it lived under `development/alter_move_prob_train/` until 2026-07-25, where the gitignored weights made a fresh clone fail in the constructor with no explanation. Only the data-generation/training/evaluation scripts remain in `development/`, and they now train *into* the live weights path — retraining overwrites what the engine loads.
- `common/search_constants.py` — search-breadth and scan-width tuning constants (candidate-move counts, sharpness/premove scan widths, mood breadth deltas) extracted from `engine.py`; documented per-constant in the file.
- `engine_components/opening_book.py` — shared repertoire/general-book consultation, see Opening repertoire above.
- `clients/mp_original.py` — the only client (mouse automation, game loop, scan-reliability guards). Five older variants were deleted on 2026-07-25 (unreferenced, untouched since their initial commit); `git log --diff-filter=D` finds them if a behaviour comparison is ever needed.
- `sites/` — *how a site behaves* (game start/end recognition, result presentation, resign/lobby click flows), as opposed to `auto_calibration/`'s *where things are on this screen*; a profile binds the two via `calibration_info.site`. Sites never import a client — they return a description and the client does the logging/state mutation. Design notes and per-site measurements: `docs/site-abstraction.md`. chess.com's two hard cases, both because its clock never moves between game states: game *end* is the dark result modal over the board centre (a clock at "end coordinates" carries no information there), and game *start* needs positive evidence of a game page — the move-nav bar under the moves list — because the lobby renders a start-position preview board beside a full clock and so looks identical to a game that just began. Same root cause behind `Site.live_game_on_screen()` (the guard that stops `new_game()` seeking over a running game): "a clock is readable" is Lichess's answer and is true on every finished chess.com board, so chess.com asks whether a clock is *ticking* instead — affordable there because it runs between games, unlike in `detect_new_game`.
- `common/utils.py` — `scraped_fen_sanity_issues()` / `InvalidPositionError`: reject structurally impossible scraped positions (e.g. king hidden by a capture animation); the engine refuses to analyse them (Stockfish segfaults) and the client discards the scan. Two layers: the default checks **placement only** — the raw scrape FEN always claims white to move, so turn-dependent tests would false-positive (a live game froze when we were black in check and every scan was rejected). `turn_reliable=True` — used only in the engine, where `update_info` asserted turn == side — additionally flags `OPPOSITE_CHECK` (side not to move in check), which segfaults Stockfish deterministically and otherwise defeats the crash-restart handler. Don't merge the layers in either direction.
- `chessimage/image_scrape_utils.py` — screen capture, FEN extraction, clock OCR, rating OCR. `rating_from_words()` picks the rating out of an OCR'd player line rather than assuming the crop is the number: chess.com writes it inline after a variable-length username (`squishypup (1453)`), so a **bracketed** 3-4 digit word wins outright (any bracket glyph — tesseract reads `(1429)` as `{1429)` about as often), and a bare number is only accepted when it is the line's sole word, which is the Lichess crop. Without that last rule a username's own digits (`analysis` `2013`) read as a rating. `capture_rating` is called once per game at setup, when chess.com shows the inline layout; the pre/post-game layout moves the rating onto a second line and correctly reads as None. Last-move highlight detection matches against BGR colours built from `FALLBACK_COLOUR_SCHEME` in `auto_calibration/config.py`; those must never sit within tolerance of Lichess's *selected-square* tint (a stale selection left by a cancelled premove otherwise reads as a last-move highlight and poisons turn detection — guarded by `testing/client/test_highlight_colours.py`).
- `auto_calibration/` — fits board/UI coordinates from screenshots; profiles stored in `auto_calibration/calibrations/`. Nearly everything derives from the detected board and clock and is site-independent; the exception is the **player/rating rows** (`CoordinateCalculator._calculate_ratings*`), because Lichess puts player info beside the clock in the right panel while chess.com puts it above and below the board and never swaps the two rows by colour (we are always the bottom player). Fitting chess.com with the Lichess geometry put the crop 100px right of the rating and read `53)` — no game detected a rating at all until 2026-07-25.
- `common/move_timing.py` — the timing formulas (mouse-leg duration, settle sleeps, drag-vs-click probability, ponder/scramble waits, MOVE_DELAY constants) shared between the live client and the simulator. Tune durations here, not inline in the client, or the two drift apart.
- `simulation/` — offline bot self-play with **simulated** clocks (no display/mouse; wall time ≈ engine compute only). `python -m simulation.run --games N --tc 60+0 --workers 5` writes PGNs with integer-second `[%clk]` that feed straight into cheat_detection (`--player SimBotWhite SimBotBlack`); workers parallelise near-linearly (each owns an Engine pair — keep ~cores/3; GPU doesn't help, the cost is CPU Stockfish). The two bots can differ per persona — `--a-*`/`--b-*` set name/rating/difficulty/quickness/mouse (`BotSpec` in `game_runner.py`; per-engine quickness works because `Engine(quickness=...)` overrides the global per instance) — and `--sides alternate` swaps colours each game with correct per-game PGN headers; `--plain` gives line-based progress for the GUI tab. Per-move clock charge = detection + max(time_take − MOVE_DELAY, compute) + mouse gesture, with the live client's fast paths (premove fire, ponder-dic hits, scrambles) reproduced in `client_model.py`. Machine-specific latency distributions come from `python -m simulation.calibrate {detection,compute}` (JSONs in `simulation/calibration/`, gitignored). Drives `Engine` (`engine.py`, delegating internally to `engine_components/`) like everything else. See its README for the charge model and Phase 2/3 roadmap (sim-vs-real Welch validation). Live sessions default to `--log-level PERF` (`main.py`) so real games accumulate `[PERF]` realised-move/scan/mouse timings for refining the model.
- `cheat_detection/` — offline human-likeness diagnostic (CLI `analyze.py`, Tkinter `gui.py` with per-feature distribution drill-down and a **Simulation** tab that drives `simulation.run` as a subprocess; see its README). Analysis depth defaults to 10 (benchmarked ~24× faster than the original 18). `long_think_rate` (emt > `long_think_secs`, default 2.0s = initial_time/30 for 60+0 — rescale for another clock) tracks the **slow** tail alongside `instant_move_rate`; it was added on 2026-07-28 after a full day of tuning the fast tail alone, which hid the larger divergence. The rating-band tables it feeds (`runs/elo_progression/report_timing.md`, `report_longthink.md`) are **tracked**, unlike everything else under `runs/` — they are the calibration target for the strength dial and cost ~65 min plus a gitignored Lichess corpus to regenerate. Bot analysis and the baseline JSON must use the same depth — mismatched depths skew every engine-derived feature; baselines store per-game feature values (`values`) for the GUI histograms and the variance test. Baselines/runs/cache/corpora are gitignored. Flagging: effect-size `|z| >= 2` (default) or Welch t-test at `--alpha` (`--test`), plus an independent Brown–Forsythe variance test (⚑v, amber in GUI) that catches un-human game-to-game *consistency* even when means match. ⚠️ Judge ⚑v flags against innocent *single accounts*, not std ratio 1.0: the baseline pools many players, so real accounts are also under-dispersed (innocent medians ~0.90 acpl, 0.46 endgame-acpl, 0.86 instant-rate; calibration write-up in `runs/single_account_calibration.md`). Use `python -m cheat_detection.subsample_check <report.json>` to check flag persistence at innocent-account sample sizes (n≈50) before tuning anything — at n=600 the test has power to flag ratios innocents share. ACPL-family variance ratios also swing heavily between identical-code 300-game sims; never tune them on one run — identical-code replicates showed a noise floor of ±0.1 mean|player_z| and ±1-2 flags per 600-unit run. ⚠️ **`blunder_rate` carries no information at 150 games/arm**: two identical-config arms measured 0.0483 and 0.0396, a gap wider than either was from the baseline, so its real between-seed spread (~0.0062) is ~3.6× the binomial standard error (~0.0017). Two confident conclusions were built on the binomial figure and had to be retracted on 2026-07-28. Settling that feature needs ~600 games/arm; `t1_rate`'s binomial error *is* sound (replicates agree to 0.8 se), so it is the accuracy feature to judge on at the 150-game price. **Mean-level judging**: don't optimise Welch flags against the pooled baseline — that tests "is the bot the *average* player", which no real account satisfies (innocents with 600 games fail several at p≈1e-10). Instead build a between-player dispersion file (`python -m cheat_detection.player_dispersion --pgn <corpus> --rating 2500 2800 --out baselines/dispersion_2500_2800.json`, minutes on a cached corpus) and judge with `python -m cheat_detection.outlier_check <report.json> --dispersion <json>`: flags |player_z| ≥ 2 or outside the empirical 2.5-97.5% band of real player means (band-only where within-player noise swamps the between signal, e.g. endgame/TP acpl), plus BF flags that persist ≥35% at n=50. Target mean|player_z| ≈ 0.8 (= E|N(0,1)|, what real innocents show) — do **not** drive every feature to 0; too-average is its own tell. Evals cache to SQLite (`cache/analysis_d<d>_mpv<m>.sqlite`, WAL, FEN-keyed) — shared across all time controls and meant to accumulate indefinitely; legacy JSON caches auto-migrate. `--workers N` (CLI + GUI) parallelises analysis game-level (~cores/2 at the default 2 engine threads); only uncached work benefits. Corpus policy: 2300+ only, meaning *at least one* player ≥2300 (`fetch_corpus --any-player --band 2300 + N`; repeatable `--band` fills several quotas in one dump pass), with the off-band opponent excluded at analysis time via `--rating 2300 9999`. Main baseline: `baselines/bullet_1plus0_2300_plus.json` (51.3k units, pure 60+0). Pair-level filters `--opponent-rating` / `--rating-diff` (own−opp, mover-centric) slice a corpus into custom comparison populations — cheap once cached; in `run`/GUI they apply to both humans and bot so the populations stay comparable. Fetches should pin one exact clock with `--tc 60+0` — mixing e.g. 30+0 with 60+0 muddies every timing feature. ⚠️ Two traps when comparing *simulated* games against a human corpus, both of which produced confidently wrong conclusions before being caught (write-up + numbers: `docs/position-conditioned-human-likeness.md`): (1) simulated PGNs stop at `CLOCK_THRESHOLD_FRACTION * initial_time` and so contain **no scramble moves**, while corpus games are complete — build a truncation-matched baseline by applying `simulation/adjudicate_result._find_cutoff_ply` to the corpus, or every bot error metric reads far too low (bot `acpl_endgame` 21.7 vs a complete-game human 294.4); (2) `blunder_rate`/`mean_wc_loss` are win-*probability* drops and saturate in decided positions, so any arm with a lopsided score rate looks falsely clean — equalise score (pure self-play, both sides same config) before comparing them across arms, and lean on ACPL and match rates, which have no ceiling. That doc also records where the bot actually diverges (match-rate deficit is entirely in *quiet* positions, ~74% of moves, where its error rates are already human — so no strength lever fixes it) and how human speed-up concentrates in forced tactical positions; all of it is 1+0-specific.
